## 步骤 2：建立极性状态与唯一模拟入口

**前置：** 原步骤 1 通过，补充步骤 1A 的最小表现结构与验收完成。

### 新增脚本

Polarity.cs、LevelPhase.cs、LevelState.cs、PolarityBody.cs、SimulationWorld.cs，以及最小 PolarityView.cs。

### 操作

1. 定义 Neutral、Positive、Negative，以及 Ready、Running、Paused、Won、Lost。
2. PolarityBody 保存初始极性配置、只读当前极性、CanMark/CanSpread/CanReceive、刚体引用和稳定 BodyId。
3. Enemy/Crate 权限均开启；玩家不作为可磁化对象。炮弹权限稍后配置。
4. World 建立有效对象注册列表。初始对象按明确列表顺序分配稳定 ID，检查重复；不用 GetInstanceID 作为重试间排序依据。
5. 启动时完成依赖建立和注册后才进入 Running；不要在未注册完时开始模拟，也不要按 Start 回调的偶然顺序决定 ID。
6. World 接管 Physics2D.simulationMode 为 SimulationMode2D.Script，在一个 FixedUpdate 中调用一次 Physics2D.Simulate(Time.fixedDeltaTime)。
7. 非 Running 状态不推进物理，Simulate 返回失败时记录错误并停止提交本步结果。
8. PolarityView 更新 VisualRoot 的主体/极性符号，显示橙色正极、蓝色负极和灰色无极性，不把整个对象连同阴影统一染色；初始化读取，后续订阅，退出时取消订阅。
9. 初期 World 中保留清楚的小方法作为阶段入口，后续逐步填入磁力、传播和伤害，不必先抽象通用系统接口。

### 验收

- [ ] 场景只有一个 Simulate 调用入口，每个固定步只推进一次。
- [ ] 动态对象仍正常碰撞，极性显示与初始配置一致。
- [ ] 停止运行后恢复 World 接管前的物理模式，不影响其他场景测试。
- [ ] 不存在脚本在各自 FixedUpdate 中重复推进模拟。

**常见问题：** 切到 Script 后物体不动，先检查 World 是否处于 Running、是否完成注册和是否真的调用 Simulate。

## 步骤 3：实现并调试吸引与排斥

**前置：** 步骤 2 通过。

### 新增内容

GameplayConfig.cs 与配置资产；磁力先作为 World 小方法，稳定后提取 MagnetismSystem.cs。

### 操作

1. 在 GameplayConfig 中配置磁力强度、作用半径、标记距离、最大加速度和安全速度上限。
2. 遍历有效对象对 i < j，任一对象 Neutral 或超过半径时跳过。
3. 按技术架构中的平滑力函数计算：同极排斥，异极吸引，给双方方向相反的力。
4. 使用 AddForce(force, ForceMode2D.Force)，不重复乘 deltaTime。
5. 根据 Wall 掩码检测磁力遮挡，箱子不阻断磁力；中心重合采用稳定分离方向，防止除零。
6. 限制异常加速度和速度，用 Gizmos 显示作用范围与方向。安全限速不要小到抹掉正常弹射。
7. 暂未实现主动标记时，通过编辑器设定初始极性后重新运行各测试，避免建立正式玩法之外的随意写状态入口。

### 验收

- [ ] 正正、负负排斥，正负吸引，含 Neutral 不产生磁力。
- [ ] 相同力下轻敌人比重箱子加速更明显。
- [ ] 超出范围或墙体隔开后没有磁力。
- [ ] 异极贴靠时没有持续剧烈抖动；中心接近重合时无 NaN 或爆速。
- [ ] 同时存在多个对象时，每对力只计算一次。

**调参顺序：** 先用两物体确认方向与尺度，再增加对象数量；先改强度、质量与阻尼，不先增加新机制。

## 步骤 4：实现玩家移动、鼠标标记与三次预算

**前置：** 步骤 3 通过。

### 新增脚本

PlayerController.cs、MarkingController.cs、MarkRequest.cs；预算保存到 LevelState。

### 操作

1. 创建 Player：根对象为脚下占地锚点，Dynamic 刚体、零重力、冻结旋转和脚下实体碰撞；VisualRoot 显示机器人身体并按根 Y 排序，独立 GroundShadow；不参与极性与传播。
2. Update 读取 WASD 并缓存方向，World 在模拟阶段驱动玩家刚体；不要直接写 Transform 运动。
3. 点击 Enemy/Crate 的可见身体也能选中：从可标记注册对象中检查主体图片的屏幕范围，按实际排序选择最前方候选并显示轮廓。忽略阴影、装饰和炮弹；请求使用根 ID，距离与遮挡按脚下位置校验，不只用小碰撞体点选。
4. 左键提交正极请求，右键提交负极请求。请求保存目标 ID、所选极性和顺序，每次点击只入队一次。
5. World 在本步最前面重新校验关卡阶段、目标有效性、权限、距离、墙体遮挡、同色与预算。
6. 有效赋极或改色扣 1 次，同色、空白、遮挡、过远等无效请求不扣。没有 Neutral 按键，没有自动回复或击杀返还。
7. 同一步多个请求顺序结算，预算不能变负。Controller 和 View 不自行修改极性或预算。
8. 先用简易调试文字显示剩余次数，完整 HUD 后续实现。
9. 如读取旧 Input API，需要在编辑器中确认 Active Input Handling 与所用输入方式匹配；本次项目包清单未显示 Input System 依赖，先不额外引入输入框架。

### 验收

- [ ] WASD 移动可控，玩家不受磁力影响。
- [ ] 点身体上部仍可选中正确对象，点阴影不会误选；前后重叠时候选与实际画面一致。
- [ ] 三次有效操作后剩余为零，再点击无法改色，但仍可移动。
- [ ] 对同色目标重复点击、点击墙或隔墙目标不会扣次数。
- [ ] 切换成相反极性消耗 1 次，并改变运动趋势。
- [ ] 快速连点不产生重复消费或负预算。

此时通过停止并重开 Play Mode 恢复测试状态即可；正式 R 重试在步骤 8 完成。

## 步骤 5：加入能受磁力影响的追击敌人

EnemyMotor.cs。

- [ ] 标记后敌人实际路线会受磁力影响，而不是仍然笔直追击。
- [ ] 玩家走位改变接触机会；敌人不瞬移或穿越箱子。
- [ ] 追击代码没有在自己的 FixedUpdate 再施力一次。

## 步骤 6：实现接触采集、去重与快照传播

**前置：** 步骤 5 通过；六敌人测试房间已就绪。

### 新增脚本

ContactRecorder.cs、接触记录数据、PropagationSystem.cs、传播候选/结果数据。

### 操作

1. 每步在主动标记之后、物理模拟之前复制有效对象的极性快照。后续炮弹生成也必须在快照之前注册。
2. 碰撞回调只复制本步数值记录，不直接改色、扣血或销毁对象。
3. 物理模拟后查询 GetContacts，补充持续接触；与回调里的短暂碰撞合并。
4. 用稳定 ID 对接触归一化和去重；双方回调、多个碰撞体不能把同一关系重复结算。接触缓冲区用满时检查扩容。
5. 只对敌人/箱子权限满足的双方计算传播：有极性接触 Neutral 产生候选；已有极性不覆盖。
6. 所有候选读取同一份快照，最后统一提交；本轮新接收者下一轮才成为传播来源。
7. 一个 Neutral 同轮遇到不同极性来源时，按本步接触冲量更大的来源决定，接近相同时按稳定 ID。冲量统计去除双边重复。
8. 传播不消耗次数，源头保留极性，主动改色不追溯修改此前已传播的对象。
9. 调试界面显示物理步编号、接触对、实际来源和接收者；传播变化使用与主动标记不同的闪光反馈。

### 验收

- [ ] A 正极，B/C Neutral，接触 A—B—C：第一轮只改变 B，下一轮仍接触才改变 C。
- [ ] 已经贴靠的两个对象，其中一个后来被标记，另一个仍可获得极性。
- [ ] 正负已带极性的对象接触，各自保留极性。
- [ ] 敌人↔敌人、敌人↔箱子、箱子↔箱子均使用同一规则。
- [ ] 传播完成后预算没有减少。
- [ ] 同一接收者同轮最多获得一个结果；改变遍历顺序不会让一轮传完整条链。

**重要：** 一步一跳解决结算顺序，不保证视觉上很慢。传播太快或立即中断时，先调整初始间距、排斥与追击，避免只靠动画把问题隐藏起来。

## 步骤 7：验收“涌现”核心，决定是否扩内容

**前置：** 步骤 1—6 完成。此时不需要伤害、美术或完整关卡。

### 实验

固定六个敌人、一个箱子和通道的初始布局，每次预算相同。分别试：

1. 给队伍前排、后排或侧面敌人正极，比较接触与传播路径。
2. 改变首次标记时机，比较聚集前和分散后的结果。
3. 给箱子负极，观察吸引和敌人同极排斥共同造成的运动变化。
4. 保留最后一次把箱子改为正极，观察能否主动改变局面。
5. 改变玩家站位，观察追击如何改变下一次接触。

用下面的格式简短记录，保持一次只改一个变量：

| 实验 | 起点/时机 | 观察到的传播变化 | 运动变化 | 玩家能利用什么 |
| --- | --- | --- | --- | --- |
| A | 待填 | 待填 | 待填 | 待填 |
| B | 待填 | 待填 | 待填 | 待填 |

### 验收

- [ ] 同一布局能得到至少两种可解释、可复现的整体局面。
- [ ] 玩家能通过少量干预改变传播路径或群体运动。
- [ ] 能指出候选用途，例如拆开追击队伍、引导位置或制造撞击。
- [ ] 结果不是无论从谁开始都全体染色后同样四散。

此阶段只证明反馈和候选用途，尚未证明真实击杀与通关价值；在步骤 8—9 加入伤害和炮台后继续验证。

**未通过时：** 暂停扩关，逐项检查接触是否有效、追击是否覆盖受力、力与质量比例、初始间距和墙体布局。敌人带动箱子属于候选战术，不能为了实现宣传案例强行加入隐藏“战车模式”。

## 步骤 8：实现伤害、胜负与快速重试

**前置：** 步骤 7 的反馈验收通过。

### 新增脚本

Health.cs、DamageSystem.cs、LevelController.cs 与伤害/死亡结果数据。

### 操作

1. 给玩家与敌人加入生命。玩家先按三次受击设计，敌人生命和撞击阈值按实际调试。
2. 使用碰撞时记录的法向相对速度判断撞击，低速贴靠不计伤；不能用碰撞后已经变慢的速度反推。
3. 归一化碰撞对，去掉双方回调造成的重复伤害，并配置短暂受伤间隔。
4. 给尖刺创建 Hazard 触发区，伤害记录进入统一结算，不进入传播记录。
5. 每步先结算伤害并标记死亡，再计算传播；死亡来源和接收者都排除。注销、Destroy 最后集中处理。
6. 敌人清空且玩家存活时胜利，玩家死亡时失败；同一步双方条件满足时沿用技术架构的玩家死亡优先判负规则。
7. 标记用完不判负；失败或通关后停止 World 的危险模拟。
8. R 重试通过重新加载 Game 场景恢复初始状态，恢复正常时间倍率并清理请求、事件、接触、冷却和 ID。
9. 统一胜负与 Ready/Running 状态，防止注册尚未完成时因敌人数暂为零而误判通关。

### 验收

- [ ] 高速箱子撞敌人或敌人撞墙能造成伤害，缓慢贴靠不会持续磨血。
- [ ] 同一次碰撞不因双边回调重复扣血。
- [ ] 本步死亡对象不参与传播，也不保留可传播尸体。
- [ ] 真实战斗中已验证的群体变化确实能带来避险或击杀机会。
- [ ] R 恢复三次预算、初始极性、生命和位置，没有旧请求立即执行。
- [ ] 胜负后仍可重试，最后一个敌人死亡后不再受到残留危险攻击。

## 步骤 9：加入炮台和默认负极炮弹

**前置：** 步骤 8 通过，已有稳定重试流程。

### 新增脚本

Turret.cs、Projectile.cs 与对应 Prefab。

### 操作

1. 炮台固定，带实体碰撞，不参与磁力、不计入清除目标。
2. 由 World 调用炮台模拟计时：瞄准玩家、预警、锁定方向、生成炮弹。
3. 炮弹为 Dynamic，gravityScale = 0，初始负极；CanMark、CanSpread、CanReceive 全部关闭，仍注册到磁力列表。
4. 在快照和施力之前完成本步新炮弹初始化与注册，生成位置避开炮台实体内部。
5. 炮弹大而少，速度留出明显偏转时间，必要时使用 Continuous 检测；没有主动追踪和范围爆炸。
6. 命中由 DamageSystem 统一消费，一颗炮弹只处理一次有效命中；撞箱子、墙或固定障碍则销毁。
7. 队伍里的正极敌人能引导负极炮弹，Neutral 敌人不产生磁力；炮弹撞 Neutral 不传负极。
8. 标记查询排除 Projectile，UI 不给炮弹显示可标记候选。

### 验收

- [ ] 预警方向清楚，炮弹发射后只受物理与磁力影响。
- [ ] 玩家能利用正极敌人引导炮弹，借敌方火力造成伤害。
- [ ] 炮弹不能标记、不能传播，命中不会重复伤害。
- [ ] 箱子能挡弹，最高设计速度下没有频繁穿墙。
- [ ] 新炮弹进入模拟、被消费和注销时都无列表修改异常。

## 步骤 11：制作教学与综合关卡，稳定配置

**前置：** 最小战斗流程完整，核心反馈可利用。

### 新增内容

LevelDefinition.cs、关卡 Prefab、关卡顺序和切关逻辑。

### 操作

1. 将房间内容整理为 Level Prefab。初始物体顺序、极性、炮台节奏和预算固定，由 LevelController 完整初始化后开始。
2. 按玩法文档制作六关：极性、接触、借火、选择起点、改变通路、极性失控。

7. 统一参数到配置或 Prefab，不把质量、速度、磁力范围散落在多处硬编码。

### 验收

- [ ] 第一关能教会主动标记和改色，第二关看得见接触传播。
- [ ] 炮台教学明确炮弹默认负极、不传播且不可标记。
- [ ] 每关都能以给定预算通关，并有合理操作余量。
- [ ] 综合关能利用不同起点或时机产生不同打法。
- [ ] 下一关与重试都恢复正确配置，不残留前关预算、ID 或接触。

## 步骤 12：打磨反馈并安排外部试玩

**前置：** 关卡流程能从头玩到尾。

### 操作

1. 打磨斜俯视机器人、箱子顶面/侧面、地面和墙体立面，素材接地 Pivot/子对象偏移统一；地面低饱和，极性颜色醒目，脚下接触可解释。
2. 补充四方向简化待机/移动外观与独立炮管转向，只更新视觉子对象；补充标记、传播、撞击、受伤及炮台预警。通过明暗面与贴地阴影建立体积感，实时灯光只在有余力时考虑。
3. 满屏连线时优先显示选中对象关系，避免看不清真正作用来源。
4. 邀请不了解设计的人试玩，不提前解释标准解法，记录理解障碍与自创用途。
5. 观察是否理解传播免费、改色计次、已有极性不被覆盖，以及如何利用群体变化。
6. 对反馈先修交互误解、卡死与预算问题，再增加装饰；调试 ID 和日志不放在正式界面。

### 验收

- [ ] 玩家能解释一次有趣变化的原因，并能尝试复现。

## 3. 必须保持的完整模拟顺序

即使开发中暂时没有炮台或伤害，也保留相应阶段的位置；未实现阶段先跳过，不随意移动传播到碰撞回调。

```text
Update：读取输入、选择目标、提交请求、处理菜单

FixedUpdate（仅 World 推进）：
    1. 检查 Running，顺序校验主动标记并扣预算
    2. 更新炮台、生成并注册本步炮弹
    3. 保存有效对象和极性快照
    4. 驱动玩家/敌人，计算并施加磁力
    5. 固定步推进物理一次
    6. 合并、归一化、去重实际接触与命中
    7. 结算伤害，死亡/已消费对象标记无效
    8. 根据快照计算传播，排除无效双方
    9. 统一提交传播，处理注销与销毁
   10. 检查胜负，通知 View
```

手动模拟关闭的是自动物理，不是其他脚本的 FixedUpdate。其他组件不自行推进物理或重复施力。官方说明参见 [Physics2D.Simulate](https://docs.unity.cn/cn/tuanjiemanual/ScriptReference/Physics2D.Simulate.html)。

持续接触查询使用可复用缓冲区；实体接触与 Trigger 危险区分开处理，参见 [Rigidbody2D.GetContacts](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Rigidbody2D.GetContacts.html)。
